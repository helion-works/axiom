# Axiom

**A security scanner for MCP servers and agent tooling.** Axiom looks for what is *hostile to an agent* — poisoned tool descriptions, hidden instructions, rug-pull primitives, exfiltration paths, exposed secrets, lookalike names, surfaces that change after you approved them — and **never calls a tool** to do it.

By [Helion Works](https://helionworks.com).

```bash
uvx --from axiom-scan axiom scan ./my-mcp-server        # or: pipx run --spec axiom-scan axiom …
pip install axiom-scan && axiom                        # no arguments: inventory this machine's MCP clients
```

> The PyPI name `axiom` is taken, so the distribution is **`axiom-scan`**; the command is **`axiom`**.

```
$ axiom scan tests/fixtures/evil_server.ts --no-ai --no-deps

$ axiom explain egress_sync_notes_1 --from scan.json
egress_sync_notes_1  [HIGH] data_exfiltration
```

## Headline numbers

**In-house bed 12/12 + 8/8 · DVMCP 15/15 · MCPSecBench 14/14 (server-side cases) · 1 critical false positive on a fresh sample of 50 registry servers the rules had never seen, 0 on the official reference servers.**

Read those with their qualifiers:

- **MCPSecBench was 5/14 held out** (2 partial, 7 missed) with the scanner frozen before any rule touched it. It is 14/14 only after fixes written against those cases.
- **The fresh registry sample was scanned once, with the rules frozen.** 49 of its 50 repositories were scanned (the scanner crashed on the other one; that bug is fixed and the repository has no CRITICAL). The sample has 1 CRITICAL finding and it is a false positive, so there are 0 true criticals and the count is small because almost nothing is rated CRITICAL, not because the label is precise.
- **HIGH is still noisy.** The same sample has 20 HIGH findings; read line by line, 19 are false positives and 1 is correct. Treat HIGH as "look at this", not as a verdict.
- **The first registry sample is now a tuned corpus.** It had 5,334 critical false positives before any fix and 29 after the first round; the second round of fixes was written against those 29, so its current figure (1 false positive and 1 correct capability note) shows the fixes work where they were aimed, nothing more.

Rules were **tuned on** the in-house bed, DVMCP, MCPSecBench, the official reference servers and the first registry sample (each of the last three was scored held out first, and that number is published next to the tuned one). The **second registry sample is held out**. The ledger with scores, dates, commit hashes and tuned/held-out status is regenerated by CI: [docs/COVERAGE.md](docs/COVERAGE.md). The write-ups: [LAUNCH_READINESS.md](LAUNCH_READINESS.md), [FP_BASELINE.md](FP_BASELINE.md), [HELDOUT_RESULTS.md](HELDOUT_RESULTS.md), [docs/SEVERITY.md](docs/SEVERITY.md).

## What it does

| | |
|---|---|
| **Static scan** (`axiom scan <dir \| file \| github url \| npm:pkg \| pypi:pkg>`) | Python via `ast`, TypeScript/JavaScript via tree-sitter. Builds the **Agent Surface Map** — every tool, resource and prompt an agent would be shown, with capability tags (`fs.read`, `fs.write`, `exec`, `net.egress`, `env`, `identity`, `install`), return-path literals, mutations and a **fingerprint**. |
| **Live scan** (`axiom live --command … \| --url …`) | stdio, Streamable HTTP, legacy HTTP+SSE. Reads `initialize`, `tools/list`, `resources/list` + `resources/read`, `prompts/list` + `prompts/get` (with limits). **Never `tools/call`.** `--source <dir>` compares the on-the-wire surface with the published source: a tool the source does not define is a `surface_mismatch`. |
| **Client configs** (`axiom local`, `axiom discover`) | Claude Desktop, Claude Code, Cursor, Windsurf, VS Code, Cline, Zed, Gemini CLI, Continue, project files. Lookalike server names, shared credentials, unpinned installs, shadow servers vs an allowlist. |
| **Baselines** (`axiom surface`, `baseline`, `drift`) | Store a server's fingerprint; exit 2 when what the agent sees changes. |
| **Outputs** | console, `--output json`, `--output sarif` (SARIF 2.1.0 for GitHub Code Scanning), `--output aibom` (CycloneDX 1.5 bill of materials: servers, tools, resources, prompts as components; findings as vulnerabilities). `--fail-on <level>` for CI. |
| **Provenance** | OSV advisories matched to the version the manifest declares, or to the lockfile's version when the manifest gives none (see Limitations); registry identity (`provenance_mismatch`), lookalike registry names (`registry_typosquat`), fresh publishes. `--no-deps` for offline. |
| **Local check** (`axiom check`, the no-argument run) | Inventories the MCP servers configured in this machine's agent clients and reports config findings. |

### What it detects

Tool poisoning and hidden instructions (markers, invisible Unicode, steering language, precedence claims), cross-server tool shadowing, lookalike tool and server names, rug-pull primitives (runtime registration, removal, invocation counters, self-rewritten descriptions, `listChanged`), response and resource injection, served secrets, hard-coded egress URLs, parameters that reach a file / process / network sink unchecked, parameters that ask for the agent's own context, confused deputies, excessive default scopes, identity-override parameters, unpinned runtime installs, install-time scripts, OAuth metadata carrying shell syntax, surface mismatches between source and wire, dependency advisories for the version actually locked, registry provenance. Every finding is mapped to the OWASP Top 10 for Agentic Applications and the OWASP MCP Top 10 (tables below).

### What it does not detect

- Behaviour that only exists at runtime after a tool is called (Axiom never calls one).
- Inter-procedural taint: a parameter that reaches a sink through more than one assignment or through another function.
- Whether an OAuth flow is implemented correctly; Axiom reads metadata literals only.
- Go, Rust, Java, C# servers (regex only; no Surface Map).
- Obfuscated or minified JavaScript beyond what the parser can see.
- Anything inside `node_modules`, `dist`, `build`, `tests` (skipped on purpose).

### Safety

- **Never calls a tool.** `live` sends exactly: `initialize`, `notifications/initialized`, `tools/list`, `resources/list`, `resources/read` (≤ 25 resources, ≤ 64 KB, text mime types, no `http(s)` URIs), `prompts/list`, `prompts/get` (only prompts with no required arguments). `--no-read` keeps it to the list calls.
- A live scan started with `--command` runs that command to start the server, as any MCP client would, with your user's permissions. Axiom sends it only the requests listed above. Use `--url` or a static scan for a server you do not want to run.
- Static scans execute nothing. A package target (`npm:pkg`, `pypi:pkg` or a bare package name) is resolved through its registry to its source repository, and that repository's default branch is cloned and scanned. The published archive is not downloaded, and nothing is installed.
- Nothing about your servers leaves your machine. Network calls are: OSV (`querybatch`, cached 24 h), the MCP Registry search (cached 24 h) and the usage ping below. `--no-deps` removes the first two.

### Accuracy

Two numbers, never merged: recall on benchmarks that plant findings, and false positives on corpora that should be clean. See [docs/COVERAGE.md](docs/COVERAGE.md); the severity policy every rule follows is [docs/SEVERITY.md](docs/SEVERITY.md).

### Limitations

Static analysis of what a server *says and can do* is not proof of what it *will do*. A clean scan lowers risk; it does not remove it. Severities are calibrated so that an ordinary filesystem, fetch or git server stays below HIGH; a server that legitimately needs a shell will show that as a capability. Read the evidence line before acting on a finding.

Dependency checks read the manifest and lockfiles in the root of what is scanned: `package.json` (`dependencies` only), `package-lock.json`, `requirements.txt`, `pyproject.toml`, `uv.lock`, `poetry.lock` and `Pipfile.lock`. `devDependencies`, `yarn.lock`, `pnpm-lock.yaml` and manifests below the root are not read. For OSV advisories, a version range in the manifest (`^1.2.3`) is looked up at its lowest version even when a lockfile pins a later one, so an advisory can be reported for a version that is not installed. OSV advisories are reported at MEDIUM for a direct dependency and LOW for a transitive one; the advisory's own rating is not used.

### Related work

Axiom is one of several open-source MCP scanners. [`SaravanaGuhan/mcp-guard`](https://github.com/SaravanaGuhan/mcp-guard) is a lightweight guard focused on blocking risky tool calls; [Invariant Labs' `mcp-scan`](https://github.com/invariantlabs-ai/mcp-scan) pioneered tool-poisoning and rug-pull checks against live servers; [Snyk's `agent-scan`](https://github.com/snyk/agent-scan) covers agent frameworks broadly; [Cisco's `mcp-scanner`](https://github.com/cisco-ai-defense/mcp-scanner) combines YARA, LLM and API analyzers. Axiom's distinct pieces are the language-independent Surface Map with a fingerprint, replayable findings, held-out scoring with published before/after numbers, and the AIBOM.

## Usage ping (anonymous, opt-out)

`axiom check` (and the no-argument run) sends at most once per 24 hours, on a background thread with a 3-second timeout that the command waits for before it exits, exactly this and nothing else:

```json
{"schema": 1, "install_id": "6f1c…-uuid4", "client_version": "0.6.0", "os": "linux", "python": "3.12",
 "counts": {"clients_detected": 2, "servers_inventoried": 7, "findings_critical": 0, "findings_high": 1,
            "findings_medium": 3},
 "sent_at": "2026-11-04T21:00:00Z"}
```

`os` is `windows`, `macos`, `linux` or `other`. Never server names, tool names, paths, env var names or values, config contents, hostnames or usernames. `axiom telemetry show` prints the exact JSON; `axiom telemetry off`, `AXIOM_TELEMETRY=0` or `DO_NOT_TRACK=1` disable it; `axiom telemetry reset` issues a new random install id. `scan`, `live` and `local` never send anything.

## OWASP Agentic AI Top 10 Coverage

Axiom is the first MCP security scanner with explicit coverage mapping to the OWASP Top 10 for Agentic Applications (2026). Every scan finding references the ASI category it maps to.

| ASI | Risk | Axiom Coverage | Detection Method |
|-----|------|:-----------------:|------------------|
| ASI01 | Agent Goal Hijack | ✅ Strong | Tool poisoning detector, instruction injection, cross-server tool shadowing, invisible Unicode, sleeper patterns; server instructions, resources and prompts are scanned statically and on the wire |
| ASI02 | Tool Misuse & Exploitation | ✅ Strong | Toxic tool combination analysis, tool over-scoping, cross-capability risk mapping |
| ASI03 | Identity & Privilege Abuse | ✅ Strong | Per-tool file read/write, env dump and shell-exec findings, excessive schema scopes, confused-deputy tools, local config credential audit, shared credential detection |
| ASI04 | Supply Chain Vulnerabilities | ✅ Strong | Dependency CVEs (OSV.dev), npm lifecycle hooks, unversioned npx, known MCP CVE database, confusable (homoglyph) tool names, runtime add_tool/remove_tool rug-pull primitives |
| ASI05 | Unexpected Code Execution | ✅ Strong | eval/exec detection, dynamic import analysis, code generation from input, VM context patterns |
| ASI06 | Memory & Context Poisoning | 🟡 Partial | Memory/context write patterns, RAG poisoning vectors, session persistence detection |
| ASI07 | Inter-Agent Communication | 🟡 Partial | Transport security, A2A protocol patterns, agent identity spoofing detection, A2A agent card scanning (`axiom a2a`: auth, signatures, poisoned skills). Live A2A message inspection remains a gap |
| ASI08 | Cascading Failures | 🟡 Partial | Blast radius estimation from tool capabilities and finding severity |
| ASI09 | Human-Agent Trust Exploitation | ✅ Strong | Claimed-vs-actual AI analysis, deceptive output detection, consent bypass patterns |
| ASI10 | Rogue Agents | 🟡 Partial | Self-modification detection, persistence mechanisms, evasion patterns, autonomous action indicators |

**6 strong, 4 partial.** Partial categories (ASI06-08, ASI10) require runtime behavioral monitoring for full coverage — Axiom's static analysis detects the code patterns that enable these attacks. Run `axiom owasp --framework all` to see the detectors and coverage notes behind each row.

## OWASP MCP Top 10 Coverage

OWASP also publishes a dedicated [OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/). It is a **beta release** (v0.1), so its IDs and titles may still change. Findings carry these references in an `owasp_mcp` field alongside `owasp_asi`. The mapping is stored as data in `data/owasp_mcp_top10.json`, so it can be updated without a code change.

| ID | Risk | Axiom Coverage | Reason |
|----|------|:-----------------:|--------|
| MCP01 | Token Mismanagement & Secret Exposure | 🟡 Partial | Regex-based secret detection in server source and client configs plus env-var exposure checks; no entropy analysis, git-history scan, or token lifetime/passthrough checks. |
| MCP02 | Privilege Escalation via Scope Creep | ✅ Strong | Permission over-scope patterns, toxic tool-capability combinations, path-escape checks and env-var over-exposure in configs. |
| MCP03 | Tool Poisoning | ✅ Strong | Hidden instructions in tool metadata, cross-server shadowing, invisible Unicode, confusable names, rug-pull primitives (add_tool/remove_tool, listChanged), plus runtime diffing between source and live tool definitions. |
| MCP04 | Software Supply Chain Attacks & Dependency Tampering | ✅ Strong | Dependency CVE lookup, known MCP CVEs, install lifecycle hooks, and unpinned npx/uvx/pip/@latest install sources. |
| MCP05 | Command Injection & Execution | 🟡 Partial | Regex, AST and Semgrep find exec/shell sinks and a heuristic flags sinks inside tool handlers, but there is no inter-procedural taint tracking from tool input to sink. |
| MCP06 | Prompt Injection via Contextual Payloads | 🟡 Partial | Injection markers in tool metadata, server instructions, resources, prompts and the strings a tool returns (static), and in instructions/resources/prompts read live; payloads produced by calling a tool at runtime are not inspected. |
| MCP07 | Insufficient Authentication & Authorization | 🟡 Partial | Flags remote servers with no visible auth and servers bound to all interfaces; does not verify OAuth implementation or per-tool authorization logic. |
| MCP08 | Lack of Audit and Telemetry | ❌ Gap | Only a low-confidence heuristic for missing logging in tool-defining files; actual audit trails and telemetry pipelines are not verified. |
| MCP09 | Shadow MCP Servers | 🟡 Partial | Covered by `axiom discover` allowlist on the local machine; no network-wide or fleet discovery. |
| MCP10 | Context Injection & Over-Sharing | 🟡 Partial | Hard-coded egress URLs in tool bodies and server-provided text, tools that send to caller-chosen destinations, and bulk-exposure heuristics; what context is actually shared at runtime is not observed. |

**3 strong, 6 partial, 1 gap.** MCP08 is labelled a gap on purpose: audit trails are a runtime property, so Axiom only offers a low-confidence static heuristic for them. MCP09 (shadow servers) is covered on the local machine by `axiom discover`, but not across a network or fleet.

## Why Axiom?

MCP servers are the new blind spot. Developers install them from GitHub with minimal vetting, granting them access to filesystems, credentials, and shell execution. The public record so far includes published vulnerabilities and demonstrations by security researchers.

Published vulnerabilities and disclosed bugs:

- **mcp-remote command injection ([CVE-2025-6514](https://jfrog.com/blog/2025-6514-critical-mcp-remote-rce-vulnerability/))** — a malicious MCP server could run commands on the client machine through a crafted OAuth `authorization_endpoint`. Versions 0.0.5 to 0.1.15; fixed in 0.1.16 (ASI04, ASI05)
- **MCP Inspector remote code execution ([CVE-2025-49596](https://github.com/advisories/GHSA-7f8r-222p-6f5g))** — versions below 0.14.1 had no authentication between the Inspector client and its proxy, so unauthenticated requests could launch MCP commands. Fixed in 0.14.1 (ASI05)
- **Filesystem MCP server symlink bypass ([CVE-2025-53109](https://github.com/advisories/GHSA-q66q-fx2p-7w4m))** — symlinks inside an allowed directory could give access to files outside it. Affects every version up to 0.6.2, and 2025.1.14 to before 2025.7.1; fixed in 2025.7.1 (ASI05)
- **Asana MCP server data exposure ([The Register, June 2025](https://www.theregister.com/2025/06/18/asana_mcp_server_bug/))** — a bug could have exposed one organization's data to MCP users in another. Asana took the server offline from 5 to 17 June 2025. The report found no indication that it was exploited

Demonstrations by researchers (not attacks on real users):

- **WhatsApp MCP tool poisoning ([Invariant Labs, April 2025](https://invariantlabs.ai/blog/whatsapp-mcp-exploited))** — a second MCP server offering a harmless "fact of the day" tool could later change its description and make an agent send the user's WhatsApp chat history to an attacker (ASI01)
- **GitHub MCP prompt injection ([Invariant Labs, May 2025](https://invariantlabs.ai/blog/mcp-github-vulnerability))** — a malicious issue in a public repository could make an agent copy data from the user's private repositories into a public pull request. Invariant describes it as a design problem in agent systems, not a bug in the server's code (ASI01, ASI03)

Axiom scans MCP servers and client configurations for patterns of this kind, including hidden instructions in tool descriptions, descriptions that change after approval, and shell syntax in OAuth metadata. [What it detects](#what-it-detects) and [what it does not detect](#what-it-does-not-detect) are listed above. Axiom was not run against the original software in these cases, with one exception: the CVE-2025-6514 pattern in the MCPSecBench benchmark, which it catches ([HELDOUT_RESULTS.md](HELDOUT_RESULTS.md)).

## Features

### 🔌 Live Server Scanning (NEW in v0.3)
Connects directly to running MCP servers via stdio or SSE transport, performs the JSON-RPC handshake, and introspects tools/resources/prompts at runtime. This catches what static analysis cannot: tool description mutations between source and runtime, hidden tools injected via compromised dependencies, and runtime-only poisoning. The `--compare` flag diffs runtime definitions against source code — if they differ, something in the supply chain changed the server's behavior.

### 🎣 Tool Poisoning Detection (ASI01)
Analyzes MCP tool descriptions for hidden instructions that manipulate AI behavior — the #1 MCP-specific attack vector. Detects instruction injection, data exfiltration directives, tool chaining manipulation, privilege escalation attempts, Unicode hiding tricks, and sleeper patterns.

### ⚠️ Toxic Tool Combination Analysis (ASI02)
Identifies dangerous combinations of tool capabilities that create attack paths — data read + network access = exfiltration channel, code execution + network = RCE path, credential access + data write = privilege persistence. Individual tools may be safe; together they're dangerous.

### 💉 Prompt Injection Risk Assessment (ASI01)
Identifies content in MCP server code that could be used as a prompt injection vector — system prompt overrides, role injection, and instruction manipulation.

### 🔍 Claimed vs. Actual Analysis (ASI09)
Uses Claude AI to compare what tool descriptions *claim* to do versus what the source code *actually* does. Flags mismatches where code exceeds stated functionality — a key defense against human-agent trust exploitation.

### 🏠 Local Config Audit (ASI03)
Scans your machine's MCP configurations (Claude Desktop, Cursor, Windsurf, VSCode) to discover all installed MCP servers, detect hardcoded credentials, dangerous commands, over-privileged env vars, shared credentials across servers, and unauth'd remote servers.

### 🔒 MCP-Specific Code Scanning (ASI05)
Pattern detection tuned for MCP attack vectors: credential harvesting, data exfiltration, arbitrary code execution, command injection (unsanitized input in shell commands), sandbox/path escape, dynamic code generation, and code obfuscation.

### 🌐 Remote servers: Streamable HTTP and SSE

`axiom live --url http://host:port/mcp` connects over Streamable HTTP (or legacy HTTP+SSE for `/sse` endpoints, auto-detected), lists tools, reads resources and prompts, and reports a server that accepted the session without any credential. Add `-H "Authorization: Bearer …"` for authenticated servers. Verified against all 15 Damn Vulnerable MCP (DVMCP) challenges.

### 📡 Transport Security Analysis (ASI07)
Checks whether MCP servers use secure transports, proper authentication, safe session management, and detects inter-agent communication patterns that could be exploited.

### 🗄️ Known MCP CVE Matching (ASI04)
A short built-in list of published MCP CVEs (three in this release: CVE-2025-6514 in `mcp-remote`, CVE-2025-49596 in `@modelcontextprotocol/inspector`, CVE-2025-53109 in `@modelcontextprotocol/server-filesystem`), matched against the entries in `dependencies` of the root `package.json` and the packages in the root `package-lock.json` (one version per package name). The lockfile's version is used when there is one, otherwise the manifest's version if it is pinned exactly. An affected version is reported (at the advisory's severity for a direct dependency, one level lower for a transitive one), a patched one is not, and a range with no lockfile gets a note, not a verdict. A package scanned by name is matched on the version written in the target, or on its latest published version. It works offline, and `axiom local` and `axiom check` do not use it. Dependencies are also checked against OSV.dev for known vulnerabilities.

### 💥 Blast Radius Estimation (ASI08)
Estimates the potential impact if a server is compromised, based on its tool capabilities, finding severity, and access breadth — helping you prioritize remediation.

### 📊 Repository Health Signals
GitHub metadata analysis: stars, contributor count, commit recency, license, archive status — low-signal repos are higher risk.

### 🕵️ Shadow MCP Discovery (NEW in v0.5, MCP09)
Inventories every MCP server configured on this machine across Claude Desktop, Claude Code, Cursor, Windsurf, VS Code, Cline, Zed, Gemini CLI, Continue and project-level config files. For each server it records the transport, install source and version pin. It keeps environment variable *names* only and redacts anything that looks like a credential. Compare the inventory against an allowlist and every unapproved ("shadow") server becomes a finding.

### 🤝 A2A Agent Card Scanning (NEW in v0.5, ASI07)
Statically checks an Agent2Agent (A2A) agent card: HTTPS, schema validity, missing or weak authentication, JWS card signatures, poisoned skill descriptions, dangerous skills exposed without auth, and extended-card exposure. It is passive only; see [A2A Scope](#a2a-scope).

### 🧭 Threat Model Generation (NEW in v0.5)
Turns scan, discovery and A2A results into a system model, then into a deterministic threat model tagged with STRIDE, CSA MAESTRO and both OWASP lists. The report includes a Mermaid data-flow diagram, attack paths and mitigations grouped by owner. See [Threat Model](#threat-model).

## Quick Start

```bash
# Clone and setup
git clone https://github.com/helion-works/axiom
cd axiom
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # Add ANTHROPIC_API_KEY for AI analysis

# Scan an MCP server (static — source code analysis)
python cli/axiom_cli.py scan https://github.com/user/my-mcp-server

# Live-scan a running MCP server (runtime — connects and introspects)
python cli/axiom_cli.py live --command npx --args "-y,@modelcontextprotocol/server-filesystem,/tmp"

# Live-scan all your local MCP servers
python cli/axiom_cli.py live

# Audit your local MCP installations (config-level)
python cli/axiom_cli.py local

# View OWASP Agentic AI Top 10 coverage matrix (add --framework mcp for the MCP Top 10)
python cli/axiom_cli.py owasp

# Inventory every MCP server configured on this machine (shadow MCP discovery)
python cli/axiom_cli.py discover

# Threat-model a server from a saved scan
python cli/axiom_cli.py scan https://github.com/user/my-mcp-server --output json --no-ai > scan.json
python cli/axiom_cli.py threatmodel --from-scan scan.json -o threatmodel.md

# Start the web dashboard
uvicorn main:app --reload
# Open http://localhost:8000
```

## CLI Usage

```bash
# ---- Static Scanning (source code) ----
axiom scan https://github.com/modelcontextprotocol/servers
axiom scan my-server --url https://github.com/user/my-server
axiom scan https://github.com/user/server --output json
axiom scan https://github.com/user/server --no-ai

# ---- Live Scanning (runtime introspection) ----
axiom live                        # Scan all local MCP servers
axiom live --server filesystem    # Scan specific server by name
axiom live --command npx --args "-y,@modelcontextprotocol/server-filesystem,/tmp"
axiom live --sse http://localhost:3000/sse
axiom live --command npx --args "-y,my-mcp-server" \
    --compare https://github.com/user/my-mcp-server   # Diff source vs runtime

# ---- Local Config Audit ----
axiom local
axiom local --path ~/.cursor/mcp.json

# ---- OWASP Coverage ----
axiom owasp                           # OWASP Agentic AI Top 10 (default)
axiom owasp --framework mcp           # OWASP MCP Top 10 (beta)
axiom owasp --framework all --output json

# ---- Shadow MCP Discovery (local machine only) ----
axiom discover                                      # inventory every configured MCP server
axiom discover --allowlist approved_servers.json    # flag unapproved (shadow) servers
axiom discover --allowlist approved_servers.json --format md > mcp-inventory.md
axiom discover --scan --offline                     # + local config checks, no network
axiom discover --scan                               # + static scan of each npm/PyPI/GitHub server (network)
axiom discover --processes                          # + running MCP-like processes (local only)
axiom discover --no-defaults --config ./team/mcp.json   # read only the given config file(s)

# ---- A2A Agent Card Scanning (static, passive) ----
axiom a2a https://agent.example.com                 # /.well-known/agent-card.json (legacy agent.json fallback)
axiom a2a https://agent.example.com/.well-known/agent-card.json --format json
axiom a2a ./agent-card.json --format md             # a card saved on disk
axiom a2a http://localhost:9999 --allow-private     # your own agent on a private address

# ---- Threat Model ----
axiom scan https://github.com/user/server --output json --no-ai > scan.json
axiom threatmodel --from-scan scan.json                        # Markdown report on stdout
axiom threatmodel --from-scan scan.json --format json -o threatmodel.json
axiom threatmodel https://github.com/user/server -o threatmodel.md    # scan first, then model
axiom threatmodel --from-discover --allowlist approved_servers.json
axiom threatmodel --from-scan scan.json --from-a2a https://agent.example.com --framework maestro
axiom threatmodel --from-scan scan.json --ai                   # + AI suggestions (needs ANTHROPIC_API_KEY)
```

### `axiom discover`

Reads **only** local MCP client config files. It never reads or prints secret values: environment variable values are not copied into the inventory, and credential-like arguments, headers and URL parts (tokens, `user:pass@`, `?api_key=`, `--token` values, well-known key shapes) are shown as `[REDACTED]`.

| Flag | What it does |
|------|--------------|
| `--allowlist`, `-a` | Allowlist JSON of approved servers. Each server is classified `approved`, `unapproved` or `unknown-version` (pinned version differs); every unapproved server raises one HIGH finding (ASI04 / MCP09). Format: [docs/FILE-FORMATS.md](docs/FILE-FORMATS.md#approved-server-allowlist), example: `data/approved_servers.example.json`. |
| `--scan` | Also run the local config checks on every server, and statically scan servers that resolve to an npm/PyPI package or GitHub repo (network). |
| `--offline` | With `--scan`: local config checks only, no network. |
| `--processes` | Also list running processes that look like MCP servers (opt-in, local only; ports are not probed). |
| `--config`, `-c` | Extra MCP config file to read (repeatable). |
| `--no-defaults` | Read only the `--config` files, not the known client locations. |
| `--format`, `-f` | `table` (default), `json` or `md`. |

The client config locations for macOS, Windows and Linux are kept in `data/mcp_client_paths.json`. Example against the bundled test fixtures:

```text
$ axiom discover --no-defaults --config tests/fixtures/discover/macos/home/.claude.json \
    --allowlist tests/fixtures/discover/approved_servers.json --format md
# MCP server inventory

2 servers in 1 config files (approved 0, unapproved 1, unknown-version 1, unchecked 0). ...

| Client | Server | Transport | Source | Package / URL | Version | Env vars | Status | Config |
|---|---|---|---|---|---|---|---|---|
| claude_code | github | stdio | npm | @modelcontextprotocol/server-github | - | - | unknown-version | ... |
| claude_code | sketchy-scraper | stdio | npm | totally-legit-scraper-mcp | 0.0.1 | - | unapproved | ... |

## Findings

| Severity | Title | OWASP |
|---|---|---|
| HIGH | Unapproved MCP server 'sketchy-scraper' configured in claude_code | ASI04, MCP09 |
```

### `axiom a2a`

`axiom a2a <base-url | card-url | path/to/agent-card.json> [--format table|json|md] [--allow-private]`

Checks an A2A agent card against A2A specification 1.0.0 (0.2/0.3 cards are accepted and reported as legacy). Findings map to the ASI categories, mainly ASI07, with ASI03 for identity and auth. Where an MCP Top 10 item is a sensible analogue (for example MCP07 for missing auth), it is listed under `related` rather than `owasp_mcp`, because an agent card is not an MCP artefact. Read the [A2A Scope](#a2a-scope) section before scanning anything you do not own.

For JWS signature verification and full JSON-schema validation, install the optional extra:

```bash
pip install "axiom-scan[a2a]"     # PyJWT[crypto] + jsonschema
```

Without the extra, `a2a` still runs. It falls back to a structural schema check and reports signed cards as `a2a-signature-unverified` (MEDIUM).

### `axiom threatmodel`

`axiom threatmodel [TARGET] [--from-scan FILE]... [--from-discover] [--from-a2a FILE|URL]... [--framework maestro|stride|both] [--ai] [--format md|json] [-o FILE]`

| Flag | What it does |
|------|--------------|
| `TARGET` | MCP server to statically scan first (GitHub URL, npm or PyPI package; network). |
| `--from-scan` | Saved scan JSON (`axiom scan --output json`, or a `ScanResponse` from the API). Repeatable. |
| `--from-discover` | Run local discovery (no network). Accepts `--allowlist`, `--config` and `--no-defaults` like `discover`. |
| `--from-a2a` | A2A agent card file or URL, or a saved `a2a --format json` result. Repeatable. |
| `--framework` | Tagging shown in the Markdown report: `maestro`, `stride` or `both` (default). JSON always carries both. |
| `--ai` | Add clearly separated AI suggestions. See [what is sent](#what---ai-sends). |
| `--format`, `-f` | `md` (default) or `json`. |
| `--output`, `-o` | Write the report to a file instead of stdout. |

Sources can be combined; they are merged into one system model. See [Threat Model](#threat-model) for what the report contains.

### CLI Exit Codes (CI/CD)

| Code | Risk Level |
|------|-----------|
| 0 | Safe / Low |
| 1 | Medium |
| 2 | High / Critical |

The newer commands use their own exit codes. `discover` exits 1 when `--allowlist` is given and an unapproved server is found. `a2a` exits 1 when any HIGH or CRITICAL finding is reported. `threatmodel` exits 0 when the report is generated. All three exit 2 on usage or input errors.

## A2A Scope

`axiom a2a` is **static analysis of the published agent card only**. It tells you what an agent *advertises* about its transport, authentication, signing and skills. It does not show how the agent behaves.

- **Passive.** For each scan Axiom makes at most one GET for the card, at most one GET for the signing keys (JWKS) when the signature or card references them, and at most one unauthenticated GET for a declared extended card. Given a base URL, the card is looked up at `/.well-known/agent-card.json`, falling back to the legacy `/.well-known/agent.json` only if the first is missing. Axiom never calls the agent's task, message or other A2A RPC endpoints.
- **Not covered:** live A2A message inspection. Prompt injection inside live messages, data leaking between agents and abuse of delegated authority are runtime behaviour. They remain a gap, and every report says so.
- **Authorised use only.** Only scan agents you own or are authorised to assess.
- **SSRF protection (hosted API).** `POST /api/v1/a2a` accepts only `http(s)` URLs, never file paths. It always refuses loopback, private, link-local (including `169.254.169.254`), unique-local, metadata and other non-global addresses, and the `localhost` / cloud-metadata hostnames. Each redirect hop is re-validated, never followed blindly, and connections are pinned to the vetted IP to defeat DNS rebinding. Responses are capped at 1 MB, with a 10 s timeout and at most 3 redirects.
- **CLI.** The same protections apply by default. To scan your own agent on `localhost` or a private network, pass `--allow-private` explicitly. The REST endpoint has no equivalent switch.

## Threat Model

`axiom threatmodel` (and `POST /api/v1/threatmodel`) turns what Axiom already knows into a reviewable threat model. It does not need an API key.

**1. System model.** The scan, discovery and A2A inputs are merged into one model:

- **Components:** the agent host (MCP client), MCP servers, their tools, resources and prompts, credentials (modelled from env var *names* only; values are never read), data stores, external services, and remote A2A agents.
- **Data flows:** which component sends which class of data to which other: user prompt, tool arguments, tool results, secrets, files, external content, delegation.
- **Trust boundaries:** local machine, third-party code on the local machine, remote servers and peer agents, and the internet. Flows that cross a boundary are marked.
- **Assets:** credentials, the user's conversation context, and the actions tools can take.
- **Assumptions:** anything inferred rather than observed. For example, "no human approval step is assumed for tool calls". Each one is listed in the report with its basis (`inferred` or `default`) so a reviewer can correct it.

**2. Rule catalogue.** Threats come only from the rules in `data/threat_catalogue.json` (19 rules in catalogue 0.5.0). Examples:

- exfiltration chains (a tool that reads external content alongside a tool that can send data out)
- command execution or writes with no human approval
- unauthenticated remote servers
- one credential shared by several servers
- unpinned or unapproved (shadow) servers
- poisoned tool metadata
- unsigned agent cards (peer impersonation)
- injection through a peer agent's skill output
- dangerous A2A skills exposed without auth

High-severity scan findings that no rule covers are carried over as their own threats. Each threat records:

- affected components and flows
- STRIDE category
- MAESTRO layer, plus any cross-layer spread
- OWASP ASI and MCP tags
- likelihood (1-5) and impact (1-5)
- **risk** = likelihood x impact, banded critical (>= 20), high (>= 12), medium (>= 6) or low
- mitigations by owner
- **evidence** linking back to the scan findings that support it (matching evidence raises likelihood by one)

The rule format is documented in [docs/FILE-FORMATS.md](docs/FILE-FORMATS.md#threat-rule-catalogue).

**3. STRIDE + MAESTRO.** Every threat gets a STRIDE category (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege). It is also placed in one of the seven layers of the Cloud Security Alliance's MAESTRO framework, with cross-layer threats flagged:

1. Foundation Models
2. Data Operations
3. Agent Frameworks
4. Deployment and Infrastructure
5. Evaluation and Observability
6. Security and Compliance
7. Agent Ecosystem

**4. Deterministic output.** The same input produces byte-identical output. Threat ids are derived from the affected components, results are sorted, and there are no timestamps or random values. That makes reports safe to diff and commit.

### What `--ai` sends

`--ai` is optional and only runs when `ANTHROPIC_API_KEY` is set (model: `ANTHROPIC_MODEL`). It sends **only a sanitised copy of the system model**:

- **Sent:** components (id, kind, name, trust zone and an allowlisted set of attributes such as capability flags, transport, install source and auth/pin/approval flags); data flows; trust boundaries; assets; assumptions; sources; and the schema version. Server, tool and package names are part of the model and are sent. Credential components are renamed `credential_1..N`, and every occurrence of the original name is replaced, so only their count is sent.
- **Never sent:** source code, scan findings or their text, tool descriptions, secret values, env var names, file paths, URLs, command lines, or the deterministic threats and scores.

AI suggestions appear in a separate "AI-suggested threats" section, each marked `source: "ai"`, and they never change the deterministic threats or risk scores. The report states exactly what was sent. Without an API key nothing is sent, no error is raised, and the report says AI enrichment was not run.

### Outputs

- **Markdown** (`--format md`, default): Scope; System description; Data-flow diagram (Mermaid, with trust boundaries as subgraphs); Assumptions; Threats (table sorted by risk, then details); Top attack paths (entry, pivot, impact); Mitigations by owner; Framework coverage (STRIDE, MAESTRO and OWASP); and the AI enrichment note.
- **JSON** (`--format json`): `schema_version`, `catalogue_version`, `sources`, `scope`, the full `system_model`, `threats`, `attack_paths`, `coverage` and `ai`. It is designed for import into other tools.

Excerpt from `axiom threatmodel --from-scan tests/fixtures/threatmodel/scan_exfil.json`:

```text

|---|---|---|---|---|---|---|---|---|
| TM-001-de715ba4 | Exfiltration chain: untrusted content can drive an outbound tool | fetch_webpage, send_email | I | L3 (+L1,L2,L7) | ASI01, ASI02, MCP06, MCP10 | 5 | 4 | 20 critical |
```

### Hosted deployments

Some endpoints act on **the machine running the API**, not the caller's machine:

- `POST /api/v1/scan/local` and `POST /api/v1/discover` read MCP client config files on the API host, and both accept arbitrary `config_paths`.
- The `/api/v1/scan/live/*` endpoints spawn processes there.

That is what you want for a dashboard on your own laptop. On a shared or hosted deployment, though, these endpoints expose the host. Restrict them (authentication, a reverse-proxy rule or network policy) or disable them. These endpoints are disabled (HTTP 404) when `APP_ENV=production` unless `AXIOM_ALLOW_HOST_ACCESS=1` (also `true` or `yes`) is set. `GET /health` reports `env` and `host_access` so you can verify a deployment. `POST /api/v1/a2a` only fetches public `http(s)` URLs through the SSRF guard described in [A2A Scope](#a2a-scope).
